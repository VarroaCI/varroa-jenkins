# Jenkins Versions

<!-- sources: api/v1alpha1/types.go (JenkinsVersionProfileSpec), internal/controller/versionprofile_controller.go, internal/controller/versionresolve.go, internal/controller/corecompat.go (evaluateVersionRollGate), charts/varroa/templates/version-profiles/, hack/gen-plugin-lock.sh -->

Which Jenkins versions your brood runs — and which plugins each version gets — is governed by cluster-scoped **`JenkinsVersionProfile`** objects. A profile pins a resolved plugin set and an optional JCasC overlay to a version or LTS line, and feeds the version picker in the creation wizard.

## Concepts

- A profile's `spec.version` is either an **exact pin** (three segments, `2.516.1`) or an **LTS line** (two segments, `2.516`, matching any `2.516.x`).
- This page owns the authoritative statement of **version resolution**: for a controller's `spec.version`, the operator selects a profile by **exact match → LTS-line (`major.minor`) match → the embedded plugin-lock baseline** shipped in the operator binary when nothing matches. The selected pinned plugin set governs the managed plugin lines during provisioning **and** the Connected-phase drift checks — see [Plugin pinning](plugin-pinning.md).
- **`resolveVersion`**: an LTS-line profile records the exact patch its plugin set was resolved against, and the operator deploys **that** core version — never an older patch than the pinned plugins require. This prevents the plugins-init abort (`AggregatePluginPrerequisitesNotMetException`) that a plugin-newer-than-core skew causes.
- **Leaving `spec.version` empty** (or setting it to the `lts` sentinel) is supported and pins the **embedded plugin-lock baseline** — both the deployed core image (`jenkins/jenkins:<baseline>`) and the managed plugin set come from it, so they cannot skew. It does not float to `jenkins/jenkins:latest`; a moving core against a build-time-pinned plugin set causes the same plugins-init abort described above. Pin `spec.version` explicitly when you want a specific core.
- The profile's JCasC overlay (`spec.jcasc.content`) is merged onto the composed bundle **before** variable resolution — the [composition pipeline](composed-bundles.md) step 4. `spec.jcasc.requiredPlugins` declares plugins the overlay depends on; a missing one raises a **non-blocking** warning condition (`LockJcascMismatch`), never a hard failure.
- Wizard metadata: `channel` (`lts` | `weekly`), `recommended` (the default the wizard preselects), `eol` (informational date). 
- The operator materializes each profile's `pluginSetRef` ConfigMap into an owned `<profile>-pluginset-content` ConfigMap (`status.contentRef`, condition `PluginSetReady`) — that copy is what provisioning actually reads.

Default profiles ship with the chart (`charts/varroa/templates/version-profiles/`) and are regenerated by `hack/gen-plugin-lock.sh`. As of this writing the chart ships an LTS-line profile (recommended) and a weekly profile. In multi-cluster installs, profiles are authored on the cluster that consumes them through `/api/v1/clusters/{cluster}/version-profiles` or `varroactl ... --cluster <name>`.

## How to list what's available

```bash
kubectl get jenkinsversionprofiles
kubectl get jenkinsversionprofile jenkins-version-2-555 \
  -o jsonpath='{.spec.version}{" ch="}{.spec.channel}{" rec="}{.spec.recommended}{" plugins="}{.status.pluginCount}{"\n"}'
# 2.555 ch=lts rec=true plugins=<N>
```

**Verify:** each profile shows `PluginSetReady: True` in `status.conditions` — otherwise its pinned set isn't servable and controllers on that version fall back down the resolution chain.

## How to author a custom profile

1. Create the plugin-set ConfigMap in the operator namespace. The `plugins.yaml` key holds a lock-set: `core:` seed entries plus fully resolved `plugins:` (every transitive dependency, pinned):

   ```yaml
   apiVersion: v1
   kind: ConfigMap
   metadata:
     name: jenkins-2-528-pluginset
     namespace: varroa
   data:
     plugins.yaml: |
       core:
         - artifactId: configuration-as-code
         - artifactId: git
       plugins:
         - { artifactId: configuration-as-code, version: "1971.vf9280461ea_89" }
         - { artifactId: git, version: "5.7.0" }
         # ... every transitive dependency, pinned
   ```

   > [!IMPORTANT]
   > Resolve the set **against the exact core version you'll run** — generate it with `hack/gen-plugin-lock.sh` rather than by hand. A lock resolved against a newer core than the controller runs aborts Jenkins startup with `AggregatePluginPrerequisitesNotMetException`.

2. Create the profile:

   ```yaml
   apiVersion: varroa.dev/v1alpha1
   kind: JenkinsVersionProfile
   metadata:
     name: jenkins-version-2-528
   spec:
     version: "2.528"                    # LTS line: matches 2.528.x
     resolveVersion: "2.528.2"           # the patch the set was resolved against
     channel: lts
     recommended: false
     eol: "2027-03-31"
     pluginSetRef: { name: jenkins-2-528-pluginset }
     jcasc:
       content: |
         unclassified:
           defaultFolderConfiguration:
             healthMetrics: []
       requiredPlugins: [cloudbees-folder]
   ```

   ```bash
   kubectl apply -f pluginset.yaml -f profile.yaml
   ```

3. **Verify:** `kubectl get jenkinsversionprofile jenkins-version-2-528 -o jsonpath='{.status.conditions}'` shows `PluginSetReady: True`, and `status.contentRef` names the operator-owned copy (`<profile>-pluginset-content` in the operator namespace), which `kubectl get configmap -n varroa` confirms exists.

## How to upgrade a controller's Jenkins version

1. Pick the target from the profile list (prefer a `recommended` LTS profile; avoid past-`eol` entries).
2. Edit the controller:

   ```bash
   kubectl patch controller demo -n teams-platform --type merge -p '{"spec":{"version":"2.555"}}'
   ```

3. The operator computes the new desired image and evaluates the **version-roll gate** before rolling: core-plugin compatibility is checked against the target profile's set, and the roll is held (with a condition explaining why) rather than shipping a combination that can't boot. Whether the roll then needs approval follows the controller's [reconciliation mode](../operations/reconciliation.md) — `manual` mode surfaces it for approval instead of rolling immediately.

**Verify:** the controller transitions `Connected → Provisioning → Running → Connected`, and:

```bash
kubectl get controller demo -n teams-platform -o jsonpath='{.status.phase}'
curl -sf https://<controller-host>/api/json | jq -r .version   # or check the login page footer
```

If it's held: `kubectl get controller demo -n teams-platform -o jsonpath='{.status.conditions}'` — look for the version-gate condition and reason.

## Troubleshooting

- Startup aborts with `AggregatePluginPrerequisitesNotMetException` → plugin-set/core version skew; regenerate the lock against the exact core (see [Troubleshooting](../operations/troubleshooting.md)).
- `LockJcascMismatch` warning on a profile → overlay's `requiredPlugins` not all present in the pinned set; add them to the lock (warning is non-blocking).
- Controller uses unexpected plugin versions → check which profile actually matched (exact beats line; no match falls back to the embedded baseline).
